## 1. 摘要（Abstract）与核心贡献（Core Contribution）

### 1.1 一句话总结

**RT-MD 不再逐个域名判断“哪个域名的数据外传量足够大”，而是持续统计“同一主机通过所有可疑域名可能向外发送了多少信息”，再用 Bloom Filter、Count-Min Sketch 和 Top-K 结构把这一思想实现为可在高负载 DNS 环境中运行的实时检测器。**

### 1.2 核心贡献（Contribution List）

1. **检测粒度上的改变：主机中心（host-centric）。** 将跨多个域名的疑似外传信息汇总到源主机，针对多域名拆分攻击；告警既给出主机，也给出该主机的可疑域名排名，兼顾发现与溯源。
2. **固定资源开销的在线流式设计。** 使用按主机维护的 Bloom Filter 去重、信息计数器累计、Top-K + Count-Min Sketch 记录贡献域名；在固定参数和 DNS 名称长度上界下，实现每条请求摊销意义上的常数阶处理和有界的单主机状态。
3. **把检测性能落实到运维可用性。** 除公开数据集与模拟多域名攻击，还做了真实校园网络的在线日志实验，报告误报、人力处置量、内存和吞吐。论文给出的离线检测吞吐为约 **142.7 万条查询/秒**。

### 1.3 先记住的三个判断

- **真正的关键创新是聚合对象**：从 domain / host-domain pair 转向 host，而不是发明了新的概率数据结构。
- **“信息量”是潜在可编码容量的上界估计**，不是实际泄露的文件字节数，也不是 Shannon 熵的精确估计。
- **“无检测窗口”不是“不重置”**：RT-MD 可在请求到来时立即判断，但仍以固定重置间隔限制统计状态；这会带来低速攻击与跨周期攻击的边界问题。

## 2. 引言（Introduction）：问题背景与研究动机

### 2.1 问题定义（Problem Definition）

DNS 通常用于域名解析，却也能充当**隐蔽数据外传通道**：攻击者控制某域名的权威 DNS 服务器，把敏感数据编码到查询名称的子域名部分。受害主机向组织内部递归解析器发起查询；解析链条最终把该名称送到攻击者控制的权威服务器，即便受害机不能直接访问外网，也可能完成数据外传。

![论文 Figure 1：DNS 外传以及跨多个权威域名的分流](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/figure1_attack.png)

*图 1，原论文 PDF 第 2 页：攻击者能够把同一份秘密拆分到多个域名对应的查询中；检测器需要识别发起行为的主机，而不能只盯住单一域名。*

例如，对外传输 `secret`，攻击者原本可能查询 `secret.attacker1.com`；现在改为分别查询 `sec.attacker1.com` 与 `ret.attacker2.com`。**每个域名的承载量减小，但主机向外泄露的总体信息并未减少**。当恶意域名增至几十个时，逐域名检测器的信号会被进一步稀释。

这里的研究目标不是预测域名是不是恶意，而是：

> **在仅观察 DNS 查询流、无法长期保存完整历史的条件下，尽早识别具有异常“新子域名信息输出”行为的内部主机，并给出可供安全运营人员追查的相关域名。**

这在校园、企业的 DNS 网关尤其重要：请求量巨大，要求处理时间稳定；误报会产生真实处置成本；一旦只能看到递归解析器的流量，源主机身份还可能丢失。因此论文强调部署位置与主机可归因性。

### 2.2 现有方法的局限（Limitations of Prior Work）

| 方法路线 | 典型代表与做法 | 关键瓶颈 |
|---|---|---|
| **单请求分类** | n-gram/bi-gram、深度学习，直接分析一个查询名称是否像隧道流量 | 看不到跨请求的累计行为；正常随机标识符和恶意编码名称可能长得很像，且面临对抗性伪装 |
| **基于时间窗的统计/分类** | 汇总查询频率、字符分布、时间频率等特征，再分类；文中举例部分方法需要最高约 1200 秒窗口以达到较好 AUC | 必须先收集足量样本，检测存在等待时间；状态与计算量随主机/域名/窗口增加 |
| **域名中心的流式统计** | **ibHH（NDSS 2024）**，以概率数据结构持续估计每个域名可承载的信息量 | 已有在线和定长状态优点，但攻击者把信息平均分到多个域名后，**单个域名的统计值可能都不越阈** |

尤其应区分 **ibHH 与传统“长检测窗口”方法**：ibHH 已经能够连续在线告警，也有周期性重置。RT-MD 的核心突破不是首次做到实时，而是**在保留该在线范式时改变统计主体**。这也是评价其创新性时必须说清楚的地方（原论文 §2.2–2.3）。

### 2.3 本文思路（Overall Idea）：把跨域攻击变成同一条累计证据

设想一台被入侵主机同时访问 10 个攻击者域名。域名级检测器看到 10 条较弱的异常线索；主机级检测器看到的却是**同一个主体在持续生成大量不重复、可承载数据的 DNS 名称**。

作者因此做了两个决定：

1. **把“本次出现了多少新的疑似外传信息”记到源主机上**，跨域名求和；重复的完全相同查询不应反复计入。
2. **主机判定与域名解释分离**：是否报警只看主机累积计数；“可能是哪几个域名造成的”则由独立的 Top-K 域名跟踪器回答。

这实际上是把检测系统拆成了两个问题：**轻量、高召回的主机级异常筛查**，以及**可近似的域名归因**。只要这两者不相互阻塞，就能同时控制每条查询的计算量与告警解释成本。

### 2.4 威胁模型与适用范围：理解论文结论的前提

原论文 §3 明确依赖以下条件：

- 内网主机使用组织可观测的 DNS 解析链路；检测器能看到**原始查询名称与源 IP**，并及时收到查询记录。
- 攻击者控制一个或多个公网域名的权威服务器，或控制反向解析区域；数据主要编码在 **QNAME 的子域名部分**，不覆盖纯时间信道、其他 DNS 字段的微弱信道。
- 作者假设解析器使用 **0x20-bit 大小写随机化**，使攻击者不能稳定依靠字母大小写再编码信息。因此模型按不区分大小写的字母表计算容量。

**重要推论**：如果某网络普遍采用未经组织解析器观察的 DoH/DoT/DoQ，或者 DNS 源 IP 是 NAT 后的共享地址，这篇论文的主机级解释就需要额外的基础设施来成立，不能直接照搬其结论。

## 3. 方法论深度解析（In-depth Methodological Analysis）

### 3.1 整体架构（Overall Architecture）：沿着 Figure 2 走一遍

![论文 Figure 2：RT-MD 完整处理流程](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/figure2_architecture.png)

*图 2，原论文 PDF 第 4 页：蓝色部分是 Query Pre-Processing Module；黄色部分是某一主机的 Information Tracking Module（ITM）；右下角输出告警及可疑域名。*

RT-MD 的输入是一条 DNS 查询，至少含有**时间戳 t、源主机 IP H 和完整查询名称 D**；输出是“继续放行”或一条包含 **H、疑似信息总量 N、Top-K 域名及各自估计值**的告警。图 2 可以读成以下数据流：

| 阶段 | 输入 → 操作 → 输出 | 这么做是为了解决什么 |
|---|---|---|
| **① 域名切分** | 完整 QNAME `subdomain.example.com` → 子域名 `subdomain` 与归属域名 `example.com` | 把“可变、可能携带数据的字段”和“用于归因的域名”分开 |
| **② Allowlist 过滤** | 归属域名匹配热门/静默期/内部名单 → 若命中则不再统计 | 排除大流量合法服务产生的随机子域名，降低误报和计算量 |
| **③ 获取主机状态** | 根据 H 查询 ITM 缓存；不存在则新建该主机的 Bloom、计数器、Top-K 和随机盐 | 所有域名共享一份**主机级累计证据** |
| **④ Bloom 去重** | 查询 `(D, salt)` 是否已访问；访问过则不累加 | DNS 重试、缓存行为不应制造新的“信息输出” |
| **⑤ 信息量量化** | 对新 QNAME 的子域名 S 估计可编码单位数 I(S)；普通 DNS 与反向 DNS 分别处理 | 把字符串长度转成便于累计、可解释的统计量 |
| **⑥ 累计计数** | 将 I(S) 加到主机计数器 N | 把多域名拆分流量重新聚拢到一个主机 |
| **⑦ 域名归因** | 以归属域名 P 为键，将 I(S) 加入 Top-K/Sketch | 在有限空间内报告主要可疑域名，供人工调查 |
| **⑧–⑨ 阈值与告警** | N 超过阈值乘以重置间隔 R → 产生告警 | 每条请求处理结束即可判断，无须等到一个统计窗口结束 |

图中还有两条容易被忽略的“管理路径”：第一，**每个 ITM 按 R 周期重置**，避免计数与 Bloom 饱和；第二，缓存采用 **2R 的 Time-to-Idle（TTI）** 策略清理长期没有非白名单请求的主机，以控制常驻状态。

**与 ibHH 的宏观区别**：ibHH 的累计主体是域名；RT-MD 的累计主体是主机。RT-MD 并非彻底不记录域名，而是把“域名记录”从**是否告警的主指标**降为**告警后的解释性辅助指标**。这个职责划分，是整个架构最值得借鉴的设计。

### 3.2 核心组件/模块拆解（Core Component Breakdown）

#### 3.2.1 模块一：查询预处理 —— “切对域名 + 尽量过滤已知良性流量”

**输入与输出**

- **输入**：查询名称 D（以及与之关联的主机、时间戳）。
- **输出**：归属域名 P、子域名 S；若 P 在白名单内，则结束后续统计。

**内部机理**

关键不只是字符串按点号切割。作者使用一个可配置后缀列表（**Configurable Suffix List，CSL**），它是 Public Suffix List 的超集，尝试识别一个攻击者能够控制、且应当为其查询行为负责的 **attribution domain（归属域名）**。

以 `u1.u2.attacker.com` 为例，若 `attacker.com` 是被识别出的归属域名，则 `u1.u2` 是可承载信息的子域名。若错误地把 `com` 当作归属域名，就会混淆不同域名；若错误地把较深层的某个动态标签当作归属域名，则可能把单个攻击者域名的流量再次打散。

对于 **反向 DNS（RDNS）**，论文做了专门规定：IPv4 的归属域名取 **/16 网络范围**，IPv6 取 **/48 网络范围**。原文例子中，`1.1.64.100.in-addr.arpa` 被切成子域名 `1.1` 与归属域名 `64.100.in-addr.arpa`。原因是攻击者还可能控制一段 IP 地址的反向解析权威区，不一定只通过普通注册域名外传。

其后是三层白名单：

1. **热门域名白名单**：论文使用 2025-04-07 生成的 Tranco Top 100 万域名列表，假设攻击者难以大规模控制这些热门域名。
2. **Peacetime 白名单**：先在假定无外传攻击的“和平期”运行监控，将被判作误报的域名纳入本地白名单；正式防护期启用该名单。
3. **内部域名白名单**：例如 `.local`、`.corp`、`.internal` 等仅在内部解析的后缀；论文附录 C 讨论，评价数据集不含这类 TLD。

**设计动机**：纯粹统计“没见过的长字符串”会把 CDN、NAS 远程访问、EDR/反病毒、邮件相关查询、动态服务标识符误认成数据外传。白名单不是可有可无的加速器，而是这套**信息上界计数法能够压低误报**的关键前提。

**代价与隐含假设**：一旦攻击者能利用热门域名下被委派、被劫持或被允许使用的子域名，相关请求可能在进入检测器主体前就被过滤；和平期若已经存在恶意外传，还可能形成“白名单污染”。这是方法的**精确率–覆盖率权衡**，不能简单理解为白名单越大越好。

#### 3.2.2 模块二：Information Tracking Module —— Bloom Filter + 主机信息计数器

**输入与输出**

- **输入**：未命中白名单的查询 `(H, D, P, S, t)`。
- **输出**：该主机的累计信息估计 N 是否增加，以及新增了多少 I(S)。

**内部机理：为什么必须去重？**

DNS 查询可能因为超时、重试或应用重复访问而多次出现。假设一台机器把同样的 `abc.attacker.com` 查询了 100 次，攻击者并没有因此获得 100 份独立的新名称信息；若逐次计数，会系统性高估疑似外传量。直观方案是为每台主机维护一套完整 FQDN 哈希集合，但它的容量会随独特查询数不断膨胀。

作者改用 **Bloom Filter（布隆过滤器）**：固定大小的位数组配合多次哈希，回答“这个完整查询名称是否很可能已经出现过”。对某主机 H，处理逻辑如下：

- 若 Bloom 认为查询 D **已出现**：不再累加；
- 若 Bloom 认为查询 D **未出现**：插入带盐的 `(D, s_H)`，然后将子域名的信息估计加到 N。

这里的盐 `s_H` 在创建 ITM 时随机生成，防止攻击者预先针对已知哈希函数构造大量碰撞。与完全精确的哈希集合相比，布隆过滤器可能发生**假阳性**：一个从未出现的名称也被判为已出现。这会**漏计信息**、降低检测灵敏度；它不是能保证绝无漏报的精确去重机制。周期性重置也用于降低布隆过滤器长期饱和的风险。

**设计动机**：主机级“新名称累计量”是检测所必需的；完整的历史名称列表却不是。因此，用受控的漏计风险换取**可预测的内存上限**。这比“每台主机一个不断增长的集合”更符合 DNS 解析器的持续运行需求。

#### 3.2.3 模块三：Top-K Domain Tracker —— 负责解释告警，而不负责决定告警

**输入与输出**

- **输入**：当前归属域名 P、主机盐以及本次新名称贡献的 I(S)。
- **输出**：主机涉及的**信息贡献最大**的 K 个归属域名及其近似累计值。

**内部机理**

如果逐域名保存完整计数，一台访问了数十万个归属域名的主机会消耗大量内存，也容易遭受资源消耗型攻击。RT-MD 采用一个**精确跟踪当前 Top-K + 近似估计其他域名**的混合结构：

- 一个固定大小的链表、一个固定大小的双向链有序哈希映射，维护 Top-K 候选及其计数；
- 一个固定大小的 **Count-Min Sketch（CMS）**，采用 **conservative update（保守更新）** 来估计其余域名的累计贡献；
- 用归属域名与主机随机盐共同形成键，并按 I(S) 而非简单的“查询次数”进行**加权更新**。

因此，查询 `x.attacker.com` 与 `verylongrandomtext.attacker.com` 给 `attacker.com` 的权重不同。**Top-K 排序依据的是潜在外传信息量，不是访问次数，也不是域名恶意概率。** CMS 可能存在碰撞引起的估计误差，Top-K 也不等于精准的攻击者域名集合。

**为什么不是先用 Top-K 再判断告警？** 因为攻击者可以把数据均摊到很多小域名，使每个域名都无法“出头”。主机总计数与 Top-K 解耦后，即使真正的外传域名不在排名里，**只要主机总计数越阈，仍然会报警**。Top-K 主要影响告警定位质量；作者在 §4.4.1 也承认，攻击者能用高流量的正常域名作诱饵，影响可疑域名名单。

### 3.3 关键公式与算法（Key Equations and Algorithms）

#### 公式一：把子域名映射为“可编码信息单位”

论文 §4.2.1 假设正常 DNS 名称中可用的、大小写不敏感的字符集合是 26 个英文字母、10 个数字及 `. _ -`，共 **39 个字符**。它不是从样本统计得到的熵，而是一个**协议允许的字符表容量模型**。

$$
I(S)=\begin{cases}
|S|, & \text{普通 DNS 查询},\\[4pt]
\left\lceil |S|\log_{39}11\right\rceil, & \text{IPv4 反向 DNS 查询},\\[4pt]
\left\lceil |S|\log_{39}17\right\rceil, & \text{IPv6 反向 DNS 查询}.
\end{cases}
\qquad
1\ \text{unit}\approx \log_2 39\approx5.29\ \text{bits}.
$$

**符号与含义**：S 是被切出的子域名字符串，`|S|` 是其字符数；39 是普通查询字母表大小，11 是 IPv4 RDNS 常见的 `0–9` 和点号，17 是 IPv6 RDNS 常见的十六进制字符和点号。`ceil`（向上取整）把较小字母表下的容量折算回普通查询的“单位”。

**公式的目标**：将长度不同、字符集不同的查询，映射到一个可加的尺度，避免将反向 DNS 的长名称当作与普通高容量子域名完全等价。

**数学直觉**：如果每个字符可从 39 种符号中任选，理论上一个字符可编码约 5.29 bit；若只有 11 种符号，每个字符最多编码约 3.46 bit，折算成 39 进制单位便是 `log_39(11)` 个。举例，IPv4 RDNS 中子域名 `1.1` 有 3 个字符，估计为向上取整的约 **2 units**，而不是 3 units。

**值得注意的边界**：DNS 对标签最长 63 字符、标签非空等规则有限制；某些字符并不能在所有位置自由选取，因此论文自己把这一计量解释为**实用编码容量的上界近似**。即使看到了 100 units，也不能倒推“攻击者实际传走了 529 bit 的秘密”；随机标识符、可预测时间戳等合法内容同样会消耗这个预算。

#### 公式二：唯一查询累计 + 主机级阈值

$$
N_H\leftarrow N_H + \mathbf{1}\!\left[(D,s_H)\notin B_H\right]\,I(S),
\qquad
\operatorname{Alert}(H)\iff N_H>\theta\,R.
$$

**符号与含义**：

- `H`：当前源主机 IP；`D`：完整查询名称；`s_H`：该主机 ITM 的随机盐；`B_H`：其 Bloom Filter。
- `N_H`：当前重置周期中，被判定为首次出现的查询所贡献的信息单位累计数。
- **指示函数**：仅当 `(D,s_H)` 在 Bloom 中尚未出现时取 1；随后系统会将其插入 Bloom，并更新域名跟踪器。
- `θ`：允许的**按重置间隔归一化**信息输出率上限，单位是 **units/s**；`R`：重置间隔（秒）。

**公式的目标**：用单一、可解释的**主机总量预算**作检测决策。这使攻击者通过多个域名分摊流量时，无法通过把每个域名的计数压低来隐藏主机总量。

**关键直觉与小例子（说明机制，并非原论文实验数据）**：设 R 为 120 s、θ 为 5 units/s，则一个周期的主机预算是 **600 units**。攻击者使用 3 个不同域名，每个域名生成 15 个不同的、长度为 20 字符的子域名：每个域名贡献 300 units，三个域名合计 **900 units**。若仅以 600 units 的域名阈值分别监控，三个域名都不报警；按主机汇总的 RT-MD 则会越过 600 units。这里用统一预算只是为了隔离“聚合粒度”的作用，**不是 ibHH 的真实阈值比较**。

**两个技术细节**：

1. RT-MD 使用的是 `N_H / R` 与 θ 比较，而**不是**用当前已过去的 `t - reset_ts` 作为分母。这是一种周期预算判定，不能将其读成任意时刻的瞬时泄露速率。
2. 系统**每处理一条查询就检查阈值**，不必等 R 秒后才出结果；但当一个重置周期结束，旧统计量被清空。**不存在预先等待满一个检测窗口**与**存在重置周期**并不矛盾。

#### 对照 Algorithm 1：核心伪代码如何落地

下面是保留论文逻辑、去掉实现细节后的阅读版伪代码（原文 Algorithm 1 位于 PDF 第 6 页）：

```text
init ITM_cache with max_hosts=M and idle_eviction=2R
for each DNS query (timestamp t, source host H, qname D):
    (S, P) = split_by_configurable_suffix_list(D)
    if P in allowlists:
        continue

    itm = get_or_create_ITM(H)
    if itm is newly created or t - itm.reset_ts > R:
        itm = new_ITM(random_salt, BloomFilter, N=0, TopK, reset_ts=t)

    if salted(D, itm.salt) is NOT in itm.BloomFilter:
        itm.BloomFilter.insert(salted(D, itm.salt))
        delta = estimate_information(S, is_reverse_DNS(D))
        itm.N += delta
        itm.TopK.update((P, itm.salt), weight=delta)

    if itm.N > theta * R:
        emit_alert(H, itm.N, itm.TopK.extract())
```

需要保留原论文中两个不那么显眼的细节：**ITM 缓存满 M 个主机时会报告资源上限异常而不是继续无限申请内存**；在阈值持续被超过的情况下，输出流**可能包含同一主机的重复告警**，因此运营侧要做关联与合并。上面的阅读版伪代码省略了达到上限的完整分支，不能代替源码。

### 3.4 为什么能做到常数时间和有界内存？

论文 §4.3 的复杂度结论为：

$$
T_{\mathrm{per\ query}}=O(1), \qquad S_{\mathrm{total}}=O(M).
$$

其中 M 是最多同时缓存的主机 ITM 数。原因是：DNS QNAME 受协议长度上限约束（通常最多 255 字节），因此切分与扫描可视为固定上界；Bloom 的哈希数、CMS 的宽度和深度、Top-K 的 K、白名单数据大小都是运行时固定配置。Top-K 更新最多遍历固定 K 个候选。

这不是说成本“无论配置怎么改都永远一样”：更大的 K、更大的过滤器以及更多的活跃主机仍会增加真实 CPU 和内存开销。哈希表操作的常数时间也通常指**期望或摊销**意义，而非所有对抗场景下的严格最坏时延保证。

**这一设计的核心取舍可以概括为**：

| 需要准确保存的内容 | 允许近似或舍弃的内容 |
|---|---|
| 主机级累计计数 N 与当前重置周期 | 查询名称的全量精确历史（用 Bloom 近似） |
| 当前排名靠前的部分域名及权重 | 所有其余域名的精确明细（用 Count-Min Sketch 近似） |
| 能够立即触发告警的检测状态 | 无限时间跨度的历史（定期重置） |

因此，它更像一个**任务驱动的流式监控系统**，而不是一个试图把所有 DNS 行为“完整理解”的复杂分类器。

## 4. 实验设计与结果分析（Experimental Design and Results Analysis）

### 4.1 实验设置（Experimental Setup）：先看清“测的是什么”

#### 数据集与攻击构造

原论文 **表 1（PDF 第 8 页）**列出三套主要数据：

| 数据集 | 组成与用途 | 主机数 | DNS 查询数 | 被标注为阳性的主机数 |
|---|---|---:|---:|---:|
| **D_Z（Ziza）** | 塞尔维亚 ISP 24 小时 DNS 数据，包含对抗性外传实验 | 35,989 | 35,074,151 | 2 |
| **D_G（GraphTunnel 混合）** | GraphTunnel 工具生成流量 + 约 26 小时校园真实背景流量；将不同工具经“伪 NAT”映射到不同源 IP | 202,445 | 781,351,105 | 19 |
| **D_M（Multi-Domain）** | 作者新构造的**全恶意**多域名外传测试集，分别模拟约 32 B/s 与约 1 B/s 的负载 | 9 | 23,361 | 9 |

D_M 包含不同数量的归属域名：32 B/s 场景分别使用 2、4、8、16、32、64 个域名；约 1 B/s 场景分别使用 2、4、8 个域名。这使其能够直接测试“域名数增加、每个域名接收到的量变小”是否破坏检测。

需要特别注意数据标签：论文 §5.1.2 在校园数据中发现**两台通过 DNS 发送递增时间戳的主机**，但作者没有把它们关联到恶意活动，认为更像合法心跳，**仍将其标注为 true positive**。因此 D_G 的 19 个阳性主机并不全部等同于“已确认入侵主机”；这影响 TPR 的安全语义，应在论文复现与后续实验中单独说明。

#### 对照方法与实验口径

- **RT-MD**：主机级潜在信息累计 + 域名 Top-K。
- **ibHH**：域名级在线信息估计。为比较主机级 TPR，作者把其检测到的域名**通过离线 DNS 日志映射回查询该域名的主机**。这是一种评估时转换，并不是 ibHH 原生的主机级实时报警实现。
- **UniqD**：作者设计的轻量基线，使用 HyperLogLog++ 估计主机访问的**独特 FQDN 数量**，以独特名称速率报警。它共享 RT-MD 的预处理和白名单，但不估算每个名称可承载的信息长度。

大多数对照使用 **120 s 重置间隔**；ibHH 的缓存大小按其原方案设为 1000 项。作者通过可接受 FPR（例如 0.01、0.001、0.0001）在数据上调整阈值；D_M 直接使用从 D_G 调好的阈值。

**指标的准确含义**：

| 符号 | 正确解释 | 不能误读成什么 |
|---|---|---|
| TPR | 主机级真阳性率：TP 主机 / 全部实际阳性主机 | 恶意查询或恶意域名的检出率 |
| FPR | 主机级假阳性率：FP 主机 / 全部实际阴性主机 | 每条 DNS 请求的误报概率 |
| **TTD** | 论文表 2、表 4 的脚注明确写的是 **Total number of detections（检测总次数）** | **不是** Time to Detect（检测时延） |
| THS | 对应方法的实际检测阈值；RT-MD/ibHH 为 units/s，UniqD 为独特 FQDN/s | 真实测得的每次攻击外传速率 |

**这一点至关重要**：看到 TTD = 680 不能写成“检测延迟 680 毫秒或 680 秒”。论文表格并没有系统报告端到端的“第一次恶意查询到第一次告警”的时延分布。

### 4.2 主实验（Main Results）：多域名聚合假设有没有被验证？

先看全文摘要所依据的**附录表 4**：作者将“可接受 FPR”设为 **0.005**（0.5%），此时在 D_G 上 RT-MD 的实际 FPR 为 **0.0039**。

![论文 Table 4：目标可接受 FPR 为 0.005 时的对比](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/table4_fpr005.png)

*表 4，原论文 PDF 第 14 页。这里的 TTD 是检测次数，THS 是检测阈值。*

为了让关键结论一眼可见，摘录两个与研究问题最相关的数据集（均为论文所报 TPR）：

| 方法 | D_G：真实背景混合数据 | D_M：多域名攻击 | D_G 实际 FPR | D_G 调得的 THS |
|---|---:|---:|---:|---:|
| **RT-MD** | **1.0000** | **1.0000（9/9）** | 0.0039 | **0.4333 units/s** |
| UniqD | 0.9474 | 0.6667（6/9） | 0.0058 | 0.2167 FQDN/s |
| ibHH（映射主机后） | 0.8947 | 0.5556（5/9） | 0.0026 | 1.0917 units/s |

**第一层结论——“以主机为中心”确实缓解了多域名规避。** 在同一组 D_M 模拟攻击下，RT-MD 检出 9/9 个恶意主机，而 ibHH 检出 5/9。该结果直接支持作者的机制假设：信息一旦被拆到多个域名，域名级累计容易丢掉信号，而主机级累计保留总量。

**第二层结论——“只统计独特 FQDN 数量”还不够。** UniqD 虽然也按主机聚合，但在 D_M 上仅检出 6/9。其问题不在于主机粒度，而在于把短标签和长标签都当成一次独特查询：数量同样是 1，可能承载的信息量却差异很大。这说明 RT-MD 的提升来自**“主机聚合 + 长度加权的信息量估计”两者结合**，而不是单独更换了聚合键。

**第三层结论——阈值更低，但不要把阈值当成实测攻击速率。** D_G 上作者能把 RT-MD 调到 0.4333 units/s，低于 ibHH 的 1.0917 units/s（大约为后者的 40%）。这是更低的**可接受统计阈值**，有利于对较小的累计异常产生告警；但表 4 的 THS 列本身**不是“成功检测实际外传速率恰好为 0.4333 units/s 的攻击”之证明**。尤其需要强调：**unit 约等于一个 39 进制字符的理论容量单位，绝非字节 B**。

**第四层结论——横向比较不是完全同一实际 FPR。** 尽管三者以相同的**目标可接受 FPR**调参，D_G 上实际 FPR 依次是 0.0039、0.0058、0.0026，因数据分布与调参阶段差异而没有严格相等。比较可作为强支持证据，但若想声称“严格同一误报率下最优”，仍需要报告完整的 TPR–FPR 曲线或统一 FPR 点上的插值。

原论文 **表 2（PDF 第 10 页）**进一步比较更严格的误报预算：

![论文 Table 2：三档可接受 FPR 下的结果](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/table2_comparison.png)

值得观察的是 D_M 随着目标 FPR 收紧的变化：

| 可接受 FPR | RT-MD TPR | UniqD TPR | ibHH TPR |
|---|---:|---:|---:|
| 0.01 | **1.0000** | 0.6667 | 0.5556 |
| 0.001 | **0.6667** | 0.5556 | 0.4444 |

另外，D_M **没有混合正常流量**，所以表中 D_M 的 FPR = 0 并不能用来证明该方法在真正混合流量环境下也没有误报；误报能力主要要看 D_Z 和 D_G。

### 4.3 吞吐与内存：检测能力之外，究竟付出了什么代价？

![论文 Table 3：资源开销与吞吐](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/table3_throughput_memory.png)

*表 3，原论文 PDF 第 10 页；桌面级 CPU（Ryzen 5 5600G）、16 GB 内存，在 D_G 上运行 5 次取均值。*

| 方法 | 平均用户态 CPU 时间（s） | 峰值内存（MiB） | 吞吐（查询/s） |
|---|---:|---:|---:|
| **RT-MD** | 262.460 | **1680.55** | **1,426,698** |
| UniqD | 228.596 | 342.519 | **1,642,800** |
| ibHH | 1061.93 | **339.007** | 355,474 |

**论文假设得到的支持**：RT-MD 相比 ibHH 的吞吐约 **4.01 倍**，CPU 时间约为其四分之一，说明作者没有仅在准确率上牺牲计算成本；Bloom 与 Sketch 的固定工作量确实具有工程收益。

**但也要看到代价**：RT-MD 峰值内存约 **1681 MiB**，比 ibHH 约 **339 MiB** 高 **4.96 倍**。它的“空间高效”主要指**每个活跃主机的状态受控、总体不会无界增长**，并不意味着它在所有对照方法里最省内存。论文另报告每个 ITM 约 **32.2 kB**；因此，“历史数据不增长”与“监控很多活跃主机时内存仍很可观”可以同时成立。

还需注意测试边界：作者在离线吞吐基准中**关闭了告警上报以避免 I/O 开销**，所以 142.7 万 QPS 是检测核心在该测试条件下的吞吐，**不能直接等同于包含日志转发、持久化、告警平台和真实解析器服务的端到端吞吐**。

### 4.4 参数敏感性：Figure 3、Figure 4 在说明什么？

**重置间隔 R（Figure 3，PDF 第 9 页）**：R 从 20 秒变到 30 分钟时，误报量通常显著下降，TP 略有下降。这不是“越长越好”——允许每周期累积的预算是 `θR`，R 越长，攻击者在一个周期内可能先传出更多数据才触发阈值。更长的统计周期与更低的误报，存在明显取舍。

![论文 Figure 4：阈值对误报数和检出数的影响](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/figure4_threshold.png)

*图 4，原论文 PDF 第 10 页：横轴为阈值，左侧纵轴为假阳性数（对数刻度），右侧为真阳性数；RT-MD/UniqD 各有启用和关闭白名单的曲线。*

**阈值 θ（Figure 4）**：阈值提高，误报迅速减少，最终也会损失 TP。RT-MD 在 D_G 上 θ 约 1 unit/s 时，能够发现全部真阳性，但约有 100 个假阳性；当 θ 升至 40 units/s 时，作者报告可保持该数据集全部恶意工具相关阳性而没有假阳性。图中**关闭白名单**的曲线误报远高于启用白名单的曲线，提示“好阈值”不能脱离组织业务模式与白名单质量讨论。

| **Peacetime 白名单** | **13,249** | 本地真实业务分布对误报控制至关重要 |
| **热门域名白名单** | **11,802** | 排除常见合法高频服务能显著降低噪声 |
| RDNS 专用量化 | 572 | 有效果，但不是本设置的主要贡献者 |

在 D_Z 同一 FPR 档位下，热门白名单减少 2,101 次、和平期白名单减少 2,140 次、RDNS 专用量化仅减少 12 次。这表明**主导精确率表现的并不是复杂数学，而是“对正常环境有多了解”**。这与 §3.2.1 中“高基数合法域名天然容易被计数器误判”的分析完全一致。

不过必须按论文图注理解：**各组件消除的误报可能重叠，不能直接把这些数加起来视为总提升**。而且图 5 主要是**误报削减组件的消融**；它没有逐一移除 Bloom、CMS、Top-K 或主机级聚合并完整报告 TP/FPR/资源成本。因此，对“哪一个算法模块带来了多少 TPR 提升”的因果归因，主要依赖不同基线的比较，而不是完整的模块级消融矩阵。

### 4.6 真实部署验证与具体实现细节

#### 真实校园流量：Figure 6 的运维价值

论文 §5.5 的**五天实验**分为：1 天生成和平期白名单，1 天调整阈值，再正式评估 3 天。作者在校园内主动测试四类外传：**Iodine**（传送 1 MB 随机数据）、**dnstt**（传送 1 MB）、**dnspot**（DNS C2 场景，列出与窃取文本文件）以及把 **10,000 个常见密码**直接作为子域名逐条发送的朴素外传。

![论文 Figure 6：人力操作、告警与在线资源使用](https://win-typora-figure.oss-cn-beijing.aliyuncs.com/%20img-win-1/figure6_realworld.png)

*图 6，原论文 PDF 第 12 页：左侧为累计人工操作，中间为告警变化，右侧为 CPU、内存与查询吞吐。*

作者报告**四种主动设置的外传场景都被检测**；仪表盘上同时待调查的告警不超过 4 个。最初 12 小时，运营人员将 12 个域名加入白名单、驳回 1 条假警并忽略 1 台持续高流量的邮件服务器；此后 60 小时，又增加了 8 条白名单操作和 8 次告警驳回，约合 **每天 6.4 次人工操作**，论文概括为初期之后约 7 次/天。

在线设备是**64 GB 内存、32 核 2.6 GHz 的虚拟服务器**；白天约处理 **1.4 万–1.6 万查询/秒**，其单线程检测进程占用一个 CPU 核心约 **7.5%–11%**，内存不超过 **1.152 GB**。这里能说明它在该校园监控流量下可运行，但不能说在线实测已经达到离线 **142.7 万查询/秒**。

**部署位置必须准确复述**：作者为避免影响 DNS 解析服务，真实试验并没有把 RT-MD 直接内联到递归解析器，而是消费**网络边界已有数据采集器转发的实时 DNS 日志**。因此论文直接测得的是**在线日志检测器的可运行性**，而非“已证明改造 DNS 递归服务器之后在高峰负载下无额外解析延迟”。

#### 代码、数据结构与复现流程

论文附录 E 与当前公开仓库显示以下实现路线：

- **实现语言与结构**：核心使用 **Rust**；源码中 RT-MD 的内部代号为 `bfcms`。`src` 包含 RT-MD、UniqD、ibHH 实现；`src/dataset.rs` 和 `src/method.rs` 对应可扩展的数据集、算法抽象；仓库还包含告警管理前端。
- **固定状态设计**：每主机一个 ITM，包含 Bloom、随机盐、计数器、Top-K/Sketch、上次重置时间；通过最大主机数 M、固定 K 和 2R 的空闲回收控制总开销。

## 5. 讨论与思考（Discussion and Reflection）

### 5.1 优点与创新点（Strengths & Innovations）

**① 选对了防御对象，而不是一味加重分类器。**

这篇论文最值得学习的地方，是作者从**攻击者的规避策略**反推出应当改变的**统计粒度**。既然攻击者可以任意增加域名，那么一个对域名分桶的检测器就会先天缺少跨桶证据；把桶改成主机，问题结构便不同了。这样的贡献看似“简单”，实际上非常扎实：它处理的是**建模单位错误**，不是试图用更复杂的模型弥补原本遗漏的信息。

**② 主判据与可解释结果解耦，工程实现干净。**

主机计数器负责“是否需要调查”，Top-K 负责“优先调查哪些域名”，Bloom 负责“什么算新信息”，CMS 负责“有限内存下跟踪长尾域名”。各模块的职责可以清楚映射到一个性能/精度问题，既方便实现，也方便按需替换组件。对系统论文而言，这比一个难以诊断的端到端神经网络黑箱更易于部署、调参和审计。

**③ 实验考虑了检测器真正落地时会遭遇的问题。**

论文没有仅报告 TPR，还讨论了高基数正常子域名、RDNS、邮件服务器、NAT、白名单维护、内存与吞吐，并提供真实校园日志测试和可操作的开源工件。这些细节说明作者知道：**能在离线分类表上得高分，并不等于适合成为 DNS 网关里的检测机制**。

### 5.2 局限性与可商榷之处（Limitations & Debatable Points）

#### 局限一：容量上界不等于真实外传信息，模型依赖“新增名称很多”

RT-MD 将每个新的、非白名单子域名的长度累加，近似的是**可承载容量**，不是流量内容的真实不可预测性，更不是未经授权数据的证据。正常系统使用随机令牌、唯一主机标识、长 URL 追踪标识、邮件验证 DNS 名称时，也会显得“信息量很高”。因此算法必须重度依赖白名单和环境适配。

反过来，如果攻击者使用**重复 QNAME 的时间间隔**编码秘密，或者把信息放在本文威胁模型之外的字段，Bloom 去重会屏蔽相同名称的大量请求。这是该信息模型刻意没有覆盖的外传途径，不构成论文内部自相矛盾，却限制了其泛化范围。

#### 局限二：没有消灭“低速潜伏”，只是提高了多域攻击的检出余量

由阈值公式可以直接推出：**只要攻击者持续把每个主机在每个重置间隔内的新增名称容量控制在阈值预算以下，检测器就可能长期不报警**。进一步地，攻击者若同时控制多台主机，可以把外传任务分配给多个源主机，每台都保持低强度——主机中心方案并未自动解决**多主机协同低速外传**。

这也是为什么我更愿意称 RT-MD 为**“低开销的主机级异常累计器”**，而不称它为“能够识别所有低速 DNS 隧道的检测器”。表 2 中严苛 FPR 条件下 D_M 的漏报，正好和这一数学边界相互印证。

#### 局限三：白名单是防误报支柱，也构成对抗者可瞄准的绕过面

热门域名可信、和平期无攻击都是较强假设。实践中可以存在域名被接管、子域名委派给第三方、合法 DNS 服务被滥用或环境初始化前已经入侵等情况。尤其是**和平期把触发过报警的域名当作误报来收集**，若缺少人工审查和周期复核，可能把已存在的外传通道一起“学习为正常”。

因此部署时最好将白名单区分为**组织能够保证内部不可外传**、**运营上已充分核验**和**仅凭流行度推定安全**几种不同的信任等级，而不是全部无条件跳过。

#### 局限四：主机身份不稳定与加密 DNS 会削弱架构优势

论文以源 IP 作为主机 ID，但 NAT 会把多台机器融合成同一条异常累计曲线，引起误报；一台机器使用多个地址或发生地址变化，则可能把其行为拆成多个计数器，引发漏报。作者在 §6 提出**NAT 层级级联部署**作为缓解，但这要求组织控制网络拓扑与 DNS 转发链路，实际部署复杂度不能忽视。

同时 RT-MD 不能直接解析加密的 DoH、DoT、DoQ 负载。组织级解析器日志仍可提供可观测性；然而若终端绕过受控解析器，或使用隐私敏感、无法合法解密的外部加密解析服务，原算法失去输入。**这不是更换一个更好的 Sketch 就能解决的问题，而是传感器位置与治理权限的问题。**

#### 局限五：内存、吞吐和“真实解析器部署”之间还有证据间隙

数据结构让每条查询的开销固定，却不代表全系统内存小。按表 3 的实测值，RT-MD 是三个方案中**峰值内存最高**的。作者声称监控单个主机约耗费 32.2 kB，但同时出现多少个活跃、非白名单主机，才是大规模部署时决定峰值内存的关键；不能把“数据里出现过的全部 IP 数”与“同时存在的 ITM 数”混为一谈。

离线吞吐实验关闭了告警 I/O；在线试验的真实 QPS 则远低于离线峰值，且没有直接嵌入 DNS 解析器。在声称“可无痛部署于大型解析器”前，还应测量**真实查询延迟、尾延迟、丢包/日志丢失、并发线程竞争、异常峰值流量和资源耗尽行为**。

#### 局限六：真实标签、样本多样性与对抗强度尚不足以闭环验证

D_Z 只有 2 个阳性主机；D_M 是 9 个模拟的全恶意主机，覆盖的编码与速率有限；D_G 中两个被算作 TP 的主机又被作者判为良性心跳。真实五天试验虽然有四种外传工具/场景，但都是**受控注入**，没有展示在未知真实攻击事件中独立发现的新型外传案例。

此外，§4.4 的安全讨论论证了加盐与 Top-K 掩护流量的风险，但还缺少系统的自适应攻击实验：例如攻击者学习重置周期、轮换域名、用合法高基数流量掩护恶意 Top-K、故意令 Bloom 饱和，或通过多主机同步分摊信息。当前实验已足以支持**“比所选基线更抗多域规避”**，但还不足以支持**“对广义自适应对抗者都鲁棒”**。

### 5.3 未来工作与启发（Future Work & Inspirations）

如果由我继续推进这条研究路线，我会按“**不破坏在线性能，逐层补上语义和攻击边界**”的原则做以下工作：

**方向一｜双时间尺度的主机累计器，针对慢速潜伏。**

在保留 120 s 左右短周期统计的同时，使用额外的紧凑 Sketch、分层计数器或衰减统计，观察数小时至数天的微弱但持续的新增名称模式。这样既能快速响应明显外传，也能为长期低速异常建立证据。要重点研究**长期累计造成的正常漂移误报**与内存预算，而不是简单延长 R。

**方向二｜轻量第一阶段 + 昂贵第二阶段，替代无限扩张的白名单。**

继续让 RT-MD 作为高吞吐的一阶段“预警器”；只有主机接近预算、或可疑域名排名异常时，再启动高成本的**条件熵、标签结构、解析响应码、NXDOMAIN 比例、会话节奏、域名委派关系**等分析。这样可以把复杂模型的推理费用集中在少量候选主机上，同时减少“合法但高基数”的误报。论文本身没有验证这个两级设计，它是一个明确可实验的扩展假设。

**方向三｜做真正与网络身份绑定的分层检测。**

将主机标识从单一源 IP 扩展为 DHCP 租约、端点 ID、VLAN/子网、NAT 映射和解析器 ID 的组合。在可取得身份映射的情况下，尝试同时维护**端点级、NAT 聚合级和组织级**异常预算。这样既能避免 NAT 误报，也有机会发现**多台受控端点共同进行低速 DNS 外传**。

**方向四｜将“可编码容量”改进为“有证据的可疑信息预算”。**

目前 I(S) 与真实信息量之间缺少对服务语义的刻画。可考虑不改变主计数器解释性的前提下，引入**子域名新颖性、可预测性、标签生成规律和历史业务基线**的置信权重；甚至给出“最坏可能外传容量上界”和“高置信可疑容量”两条曲线。但这需要防止攻击者反向优化这些权重，且不能把检测目标偷偷变成难以解释的黑箱分数。

**方向五｜建立与攻击者互动的评估基准。**

至少增加跨域名数量、主机数量、重置边界、编码方式、Bloom 饱和、诱饵正常域名、不同 NAT 拓扑和加密 DNS 可见性等轴。除 ROC/TPR/FPR 外，同时报告**实际外传字节数到首次告警、首告警延迟分布、每千主机每天人工操作数、CPU 尾延迟和内存峰值**。这会比单独强调最低阈值更接近企业防御系统的决策需求。

### 5.4 值得带入组会的五个问题

1. **如果攻击者从“多域名”进一步进化成“多主机 × 多域名”，RT-MD 的检测主体还应该是单主机吗？** 能否以较小的状态开销识别协同异常？
2. **把 QNAME 字符长度当作潜在信息量，究竟有多少可以通过真实业务的基线来校正？** 引入统计熵会改善误报，还是更容易被精心编码的攻击绕过？
3. **为什么作者选择基于 `θR` 的固定周期预算，而不是对真正经过的秒数计算速率？** 两者对于突发外传、周期边界和高峰合法业务的表现会如何不同？
4. **真正应当追求的系统指标是什么？** 是 140 万 QPS，还是“在每千主机每天 5 次人工处置预算内，最多泄露多少字节之前能阻止攻击”？
5. **如果白名单贡献了大部分误报削减，迁移到一个新的公司或国家网络时还能保持相同表现吗？** 应当设计怎样的跨网络、跨月份、存在预埋恶意样本的实验来检验可迁移性？

### 5.5 最终评价：值得带走的研究思想

> **这篇论文最有价值的观点不是“Bloom Filter + Count-Min Sketch 可以做 DNS 检测”，而是“应围绕攻击者无法轻易分散的行为主体来累计证据，再把精确告警与近似解释分层实现”。**

从科学论证来看，文章建立了一条比较完整的链条：**多域名导致域名级检测证据分散 → 主机级信息累计重新汇聚信号 → D_M、多种误报预算、吞吐实验和真实运维实验提供支持**。它的机制简单清晰、工程设计贴合约束、开源工件具有实践价值。

与此同时，必须把结论限定在**可观测的 QNAME 外传、可正确归因的源主机、足够可靠的白名单、以及固定周期信息预算**这些条件内。它并不直接解决加密 DNS 绕过、NAT 身份融合、跨主机协同和无限低速泄露；作者现有实验也尚未充分覆盖自适应对手与端到端解析器部署成本。

**一句话带走**：RT-MD 是一篇很好的“**先改变问题的统计单位，再用经典流式数据结构把新思路做实**”的系统安全论文；学习它最重要的是把检测目标、公式语义、实验口径和工程边界四者逐一对应，而不是只记住“CCF A、1.4M QPS、0.43 units/s”。
